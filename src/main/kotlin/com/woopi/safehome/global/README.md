# global — 횡단 관심사

도메인과 무관하게 앱 전체가 공유하는 공통 인프라.
**도메인은 이 계층에 의존하지만, 역방향 의존은 없다.**

> **범위**: `global/**`
> **상위**: [API README](../../../../../../../README.md) · **연관**: 레이어 규칙 → [`domain/README.md`](../domain/README.md)
> **여기 없는 것**: 클래스·메서드 목록과 설정값 — 디렉터리와 코드가 답한다.

| 인증 바인딩 | 인증 헤더를 해석해 컨트롤러 인자에 사용자 식별자를 넣는다 |

## 조용히 깨지는 것들

### 인증 인자의 타입이 다르면 인증이 사라진다

인자 리졸버는 **애노테이션과 타입이 둘 다 맞을 때만** 동작한다.
타입이 다르면 리졸버가 자기 일이 아니라고 판단하고 빠지는데, **에러가 아니라 그냥 지나간다.**

> 결과적으로 그 엔드포인트는 **인증 없이 열린다.** 컴파일은 정상이다.

리졸버가 받아들이는 타입이 무엇인지를 문서에 적지 않는다. **제약 테스트가 리졸버에게 직접 물어**
보호 대상 엔드포인트를 검사하므로, 판정 조건이 바뀌면 검사도 함께 따라간다.

### 토큰 검증 실패는 예외가 아니라 빈 값이다

검증 함수는 실패해도 던지지 않고 **비어 있는 결과를 돌려준다.**
호출한 쪽이 그 값을 확인하지 않으면 **인증 실패가 성공처럼 흘러간다.**

접근 토큰과 갱신 토큰은 서로 바꿔 쓸 수 없다. 토큰 안에 종류가 들어 있어
잘못 넣으면 **에러 없이 검증만 실패한다.**

### 토큰 서명 키에는 공개된 기본값이 있다

서명 키는 환경 변수에서 읽고, **없으면 설정 파일에 적힌 기본값을 쓴다** — 로컬에서 환경 변수 없이 바로 띄우기 위해서다.
그런데 저장소가 공개라 그 기본값은 누구나 안다. 배포 환경이 키를 빠뜨리면 서버는 **에러 없이 뜨고 로그인도 정상으로 되면서**
누구나 아무 회원의 토큰을 만들 수 있는 상태가 된다. 실제로 개발 서버가 넉 달 동안 이 상태였다.

그래서 **배포 프로파일에서 키가 없으면 기동을 거부한다.** 조용히 뜨는 것보다 뜨지 않는 편이 낫다 — 배포가 헬스 체크를
기다리므로 실패가 드러난다. 로컬과 테스트는 막지 않는다. 판정은 테스트가 고정하고, 새 배포 프로파일을 만들면 막을 목록에 더해야 한다.

**키를 바꾸면 기존 토큰이 모두 무효가 된다.** 저장된 데이터는 그대로이고 다시 로그인하면 된다.
env 파일은 컨테이너를 만들 때 읽히므로 **재시작이 아니라 새로 만들어야** 새 키가 들어간다 —
서버에서 돌리는 절차는 [`docker/maintenance/set-jwt-secret.sh`](../../../../../../../docker/maintenance/set-jwt-secret.sh) 가 갖는다.

### 읽기 전용 표시는 인스턴스를 고르지 않는다

설정에는 읽기/쓰기 인스턴스가 나뉘어 있고, 트랜잭션의 읽기 여부를 보는 인터셉터도 있다.
그런데 실행해 보면 **읽기 전용 트랜잭션도 쓰기 인스턴스를 쓴다.** 코드만 읽으면 분리가 동작하는 것처럼 보인다.
실행 테스트가 이 사실을 고정한다. 원인은 확인 안 됨 — 인터셉터가 커넥션이 잡힌 뒤에 끼어드는 것으로 보인다.

**분리를 켜려면 복제 지연부터 다룬다.** 트랜잭션 밖에서 방금 쓴 데이터를 다시 읽는 곳 — 분석 비동기 처리부가
그렇다 — 이 복제본으로 가면 작업을 찾지 못할 수 있다. 켜는 변경을 하면 실행 테스트가 깨지므로 그때 이 절을 함께 고친다.

유스케이스의 읽기 전용 기본값은 제약 테스트가 지킨다. 분리를 켤 때 조회가 읽기 인스턴스로 가는 근거가 된다.
컨텍스트를 직접 조작하지 않는다 — 설계 없이 분리를 우회해 켜는 길이다.

### 페이지 번호의 기준이 요청과 응답에서 다르다

프레임워크의 기준과 응답에 싣는 기준이 서로 다르게 변환된다.
**응답값을 그대로 다음 요청에 넣으면 한 페이지를 건너뛴다.**
정확한 기준은 저장소 README의 계약 절이 갖는다 — 클라이언트가 맞춰야 할 값이기 때문이다.

## 이름과 실제가 다른 곳

**비동기 설정 클래스가 웹 계층 설정도 함께 갖고 있다.** 스레드풀뿐 아니라
비동기 요청 타임아웃, 교차 출처 정책, 인자 리졸버 등록이 모두 여기 있다.
**CORS나 인증 리졸버를 찾을 때 이 이름을 지나치기 쉽다.**

## 설계 결정

**보안 프레임워크가 없다는 결정의 대가를 이 계층이 진다.** 위 "인증 인자" 항목의 위험이 그것이다.
왜 그렇게 정했는지와 언제 다시 볼지는 저장소 README의 결정 이유 절이 갖는다.

**비동기 요청 타임아웃과 알림 스트림의 수명을 같은 값으로 맞췄다.**
한쪽만 길면 다른 쪽이 먼저 끊어 원인을 찾기 어려운 중단이 생긴다. **둘을 따로 조절하지 않는다.**

**토큰 만료 시간은 설정 파일에 값이 박혀 있다.** 환경별로 다르게 하려면 주입 방식부터 바꿔야 한다.

**공유 열거값을 여기 둔다.** 여러 도메인과 클라이언트가 같은 값을 쓰기 때문이다.
값을 바꾸면 저장소 README의 계약 절과 클라이언트까지 함께 가야 한다.
