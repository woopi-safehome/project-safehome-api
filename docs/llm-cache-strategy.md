# LLM 캐시 전략

외부 분석 서버 호출은 느리고 비싸다. 같은 문서·같은 임대차 유형의 재요청을 캐시로 받아낸다.

> **범위**: 분석 결과 캐싱의 키 구성·무효화 정책과 그 이유
> **상위**: [API README](../README.md)
> **여기 없는 것**: 클래스·함수 이름, 키 접두사 문자열, 보관 기간의 실제 값 — 코드와 설정이 답한다.

---

## 키를 어떻게 만드나

키는 **버전 접두사 + 본문 해시 + 임대차 유형**으로 이뤄진다.

**임대차 유형을 해시에 넣지 않고 따로 붙인다.** 같은 등기부라도 유형에 따라 분석 결과가 달라지므로
독립적으로 캐싱해야 하기 때문이다. 유형이 없으면 지정되지 않음을 뜻하는 값으로 채운다.

### 해시 전 정규화 — 이 모듈의 핵심

본문을 그대로 해싱하지 않는다. **줄바꿈 형식을 통일하고, 각 줄의 앞뒤 공백을 지우고, 빈 줄을 버린 뒤**
섹션을 정해진 순서로 이어 붙여 해싱한다.

> **왜**: 문서에서 텍스트를 뽑는 라이브러리가 운영체제와 버전에 따라 **공백과 줄바꿈을 다르게 낸다.**
> 정규화하지 않으면 **내용이 같은데 해시가 달라져** 캐시가 사실상 동작하지 않는다.

**정규화는 해시 계산에만 쓴다. 분석 서버로 보내는 본문은 원본 그대로다.**
이 둘을 섞으면 분석 입력이 조용히 바뀌어, 캐시된 결과와 새 결과가 서로 다른 입력에서 나온 게 된다.

---

## 히트와 미스

```
문서 파싱 → 본문 추출
   → 정규화·해싱 + 유형 접미사로 키 구성
   → 캐시 조회
        히트 → 외부 호출 없이 그대로 반환
        미스 → 외부 호출 → 캐시에 저장 → 반환
```

**캐시 장애는 무시한다.** 연결이 실패하면 경고만 남기고 미스처럼 외부 호출로 넘어간다.
캐시는 비용 절감 수단이지 가용성의 전제가 아니다.

---

## 자동 무효화를 두지 않는다 — 검토하고 버린 선택

**등기부는 부동산마다 고유해서 히트율이 본질적으로 낮다.** 정교한 무효화를 만들 만한 이득이 없다.

분석 서버가 배포될 때 캐시를 자동으로 비우는 구조를 검토했고, **다음 이유로 채택하지 않았다.**

- 버그 수정이나 의존성 갱신 같은 **모든 배포가 캐시를 전부 날린다.** 무효화 범위가 지나치게 넓다.
- "분석 서버 배포 → 백엔드 캐시 소멸"이라는 **암묵적 결합**이 생겨 운영 예측성이 떨어진다.
- 독립 배포 구조에서 한쪽이 다른 쪽 상태를 감시하면 **책임 소재가 뒤섞인다.**

---

## 전부 비워야 할 때

분석 서버의 **프롬프트·판정 로직·지식 데이터·모델**이 바뀌면 옛 결과가 계속 나가므로 비워야 한다.
방법은 **캐시 키의 버전 접두사를 올리는 것** 하나다. 옛 키는 보관 기간이 지나면 저절로 사라진다.

> 상류에서 분석 결과를 바꾸는 변경을 했다면 **이 버전을 올렸는지 반드시 확인한다.**
> 올리지 않아도 아무 에러가 나지 않는다 — 옛 결과가 조용히 계속 나갈 뿐이다.
